# Architecture

このリポジトリの設計判断を記録する。
実装の詳細ではなく、「なぜその境界にしたか」だけを残す。

## Scope

CSA プロトコルサーバー（floodgate / 世界コンピュータ将棋選手権 / 電竜戦）と、GUI を挟まずに対局する。

- `rsshogi-csa`: CSA の行コーデック。command model / parser / formatter
- `rsshogi-csa-bridge`: session 状態機械、時間台帳、USI エンジン監督、CLI

観戦・事後検証・棋譜変換はこのリポジトリの外にある。
bridge が書く JSONL イベントログが、その境界の唯一の受け渡し口である（0011 / 0012）。

## Repository Boundary (0001)

CSA クライアントを既存 repo に入れず、新規 repo にした。

- `rsshogi` はコア board library であり、`USI / CSA サーバ` を明示的な非目標としている。
  依存も `thiserror` と `log` のみで、ここに socket と async runtime を持ち込むと crate の性格が変わる。
- `rsshogi-usi` は依存ゼロの USI 行コーデックで、session 層を持たない方針を明文化している。
- コーデックの唯一の consumer は当面 bridge であり、API 形状は bridge を書きながら確定する。
  同一 workspace の path 依存でないと、開発中の変更が publish と version bump の往復になる。

最後の理由が決め手である。

## Codec Does Not Depend on `rsshogi` (0002)

`rsshogi-csa` は `rsshogi` に依存しない。
optional feature としても持たない。

指し手は構文検証だけを行う文字列型で保持し、盤面は持たない。
`BEGIN Position` ブロックの中身は生の行のまま保持し、解釈は呼び出し側に任せる。

`rsshogi` には既に `Position::move_from_csa` と `Move32::to_csa` があるが、
これを feature 越しにラップすると、public crate 2 つの間に semver の縁ができる。
変換は bridge の端で 1 関数ずつ持つ方が安い。

結果としてコーデックは dependency ゼロを維持する。
runtime も dev も持たない。

`rsshogi-usi` の `assert_valid_transcript` は parse / format 関数を型引数に取る汎用ヘルパーで、
当初は dev-dependency として借りる想定だった。
しかし fixture の comment 記号が `#` で固定されており、CSA では `#WIN` `#RESIGN` が
すべて comment として黙って読み飛ばされる。
終局処理は最も落としてはいけない箇所なので、fixture reader は `;` を comment 記号として自前で持つ。

## Sans-I/O Session Core (0003)

危険なのは行のパースではなく、session 状態機械と時間台帳と終局バーストの組み合わせである。

session core は bridge crate 内のモジュールとして置き、I/O から隔離する。

```text
Event  = Line(CsaCommand) | EngineMsg(UsiCommand) | Tick(Instant) | Eof | ConnLost
Action = SendLine | StartGo | ArmTimer | WriteLog | Alert | ...
```

tokio 型はこのモジュールに入れない。
これにより信頼性テストが transcript の再生になる。

別 crate に切らないのは、境界の規律さえ守れば crate 分割が何も足さないためである。

## Clock Is Reconstructed, Not Estimated (0004)

サーバーの時間計算は決定的な整数演算である。
`,T` エコーを台帳に適用すれば、両者の残り時間は厳密に再現できる。

自分の手番が来た時点で、直前の自分の手のエコーも相手の手も届いている。
したがって残り時間は推定ではなく確定であり、ローカル時計と `min` を取る対象が存在しない。

ローカル時計は「今飛んでいる手の予算」という別の問題にだけ使う。

`ClockLedger` は純粋な型にし、表駆動テストで固定する。
`Time_Unit` / `Least_Time_Per_Move` / `Time_Roundup` / `Delay` を決め打ちしない。

USI へ渡すときの正規化は 2 つ。

- `byoyomi` と `binc`/`winc` は USI で併用禁止のため、サーバー指定に応じて排他的に選ぶ
- CSA の増秒は前払いなので、USI の後払い規約へ変換してから渡す

安全マージンはエンジンへの過少申告として入れる。
サーバーの `T` はネットワーク往復を含んで切り捨てられるためである。

## Proposal Acceptance Fails Closed (0014)

`Game_Summary`は対局に合意する前の入力境界である。
一行でも解釈できなければ残りを`END Game_Summary`まで読み捨て、そのproposalを`REJECT`する。
部分的に読めたclockやpositionを既定値と組み合わせて対局を始めない。

codecは未知の追加fieldを保持するが、bridgeは`Protocol_Version:1.2`、server mode、
`Format:Shogi 1.0`、必須field、positionとclockを`AGREE`前に検証する。
positionはblockの存在、終端、盤面設定行、手番行を確認し、空または未知の行を既定局面として扱わない。
時間無制限はUSIの`btime 0 wtime 0`と同義ではない。
0.1.0では新しい時間配分policyを足さず、時間無制限のproposalを拒否する。

## Engine Runs as a Subprocess (0005)

エンジンはライブラリとしてリンクせず、subprocess として USI で駆動する。

- やねうら王など他エンジンでも検証できる
- エンジンのクラッシュが bridge を巻き込まない
- `rsshogi-nnue` / `rsshogi-az` に一切変更を要求しない

エンジンプロセスは全対局を通して生かす。
`rsshogi-az` は `isready` の中で CUDA backend を構築し graph pre-capture を回すため、初回が重い。
`setoption` と `isready` は 1 回だけ行い、対局ごとは `usinewgame` だけを送る。

暖機は `LOGIN` より前に完了させる。
Game_Summary から `AGREE` までの猶予は 120 秒で、floodgate のペアリングは毎時 :00 と :30 に走る。

## Responsibility Boundary (0006)

ブリッジとエンジンの責務をここで一度だけ決める。
新しい判断を足すときは、まずこの節の表に 1 行足せるかを確かめる。

場面は 3 つに分かれる。混ぜると判断がぶれる。

- A: エンジンが答えた。その答えに介入するか
- B: エンジンが何も答えなかった。何を送るか
- C: エンジンが関与しない。ブリッジが単独で持つ

### A: エンジンが答えたとき

介入してよいのは次の 2 つを**両方**満たす場合だけである。
片方でも欠けたら、そのまま送って警報を上げる。

**規則 A1（立脚点）: 根拠がブリッジ自身の状態であること。**

ブリッジ自身の状態とは、サーバーが継続的に裏書きしているもののことである。

- 盤面。相手の手も自分の手のエコーも、すべて同じ盤面に通している
- 時計台帳。`,T` エコーから再構成しており、推定値を含まない
- 接続と phase。直接観測している
- 自分がエンジンに送った設定

エンジン自身の状態とは、エンジンにしか見えないもののことである。
評価値、読み筋、探索深さ、どの手を指すか、投了するか、宣言するか。

エンジンの評価を根拠にエンジンの判断を否定するのは循環である。
`bestmove resign` を「評価値が裏付けない」という理由で拒んでいたのはこれに当たる。
判定材料の `info score` がエンジン自身の出力だった。

**規則 A2（代替の質）: 差し替えるものが、防ごうとしているものより悪くなり得ないこと。**

`bestmove win` の検証はここで落ちた。
`can_declare_win()` は盤面に立脚しているので A1 は満たす。
しかし宣言を拒んだ先の `fallback` には読み筋が無く（宣言した探索の PV は空）、
`PanicPolicy::Resign` に落ちる。
つまり「エンジンが勝ちと判断した局面を投了する」。
防ごうとした誤宣言（即負け）より確実に悪い。

| 場面 | A1 | A2 | 挙動 |
| --- | --- | --- | --- |
| 非合法な `bestmove` | 盤面 ✓ | 読み筋 or 投了。送れば即負け ✓ | 送らない |
| `bestmove win` が検証を通らない | 盤面 ✓ | 投了に落ちる ✗ | 送る + 警報 |
| `bestmove resign` を評価値が裏付けない | エンジンの評価 ✗ | — | 送る + 警報 |
| ponder の予測手が非合法 | 盤面 ✓ | ponder しないだけ ✓ | ponder しない |
| `USI_Ponder=false` をエンジンが守らない | 送った設定 ✓ | ponder しないだけ ✓ | ponder しない |

検証コードは介入をやめた後も残してある。
判断は変えないが、警報としての価値は変わらないからである。
`UnverifiedDeclaration` と `SuspectResign` は、
エンジン側で何かが起きたことを対局後に見つけるための唯一の手掛かりになる。

### B: エンジンが答えなかったとき

ここに規則 A1 / A2 は効かない。譲る相手がいないからである。
沈黙は選択肢ではない。時計は動いており、放置すれば時間切れで負ける。
必ず何かを送る。

順序は「エンジン自身が最後に出したもの」から「最も保守的な行動」へ降りる。

1. 直前の読み筋の初手
2. 宣言勝ちが成立するならそれ
3. 投了

ブリッジが手を発明することはしない。
唯一の例外が `PanicPolicy::AnyLegal` で、明示的な opt-in である。

| 場面 | 挙動 |
| --- | --- |
| 着手期限を超過 | `stop` → grace → 梯子 |
| `bestmove` を返さないまま grace 超過 | 梯子 |
| 探索中にエンジンが死亡 | 梯子 → 再起動 |
| 手番でないときにエンジンが死亡 | 何も送らず再起動 |
| 連続して答えなかった回数が上限に達した | 投了 |

最後の 1 行だけは性質が違う。
壊れたエンジンで読み筋を指し続けても盤面は悪くなる一方なので、
どこかで止める必要がある。`max_degraded_moves` がその線である。

### C: エンジンが関与しないもの

サーバーとの間だけで完結し、エンジンに委ねる余地がないもの。
ブリッジが単独で持ち、エンジンには結果だけを伝える。

| 対象 | 扱い |
| --- | --- |
| 時計台帳 | `,T` から再構成する。推定しない |
| 提案の検証（局面・指し手・`To_Move`） | 読めなければ `REJECT` |
| 入玉宣言ルール | Game_Summary から読み、`setoption` でエンジンに送る |
| 接続と keepalive | ブリッジが持つ。切断は負けなので落とさない |
| 終局バーストの解釈 | ブリッジが読み、`gameover` に翻訳する |

千日手・入玉・最大手数の**裁定**はしない。
CSA ではサーバーが `#SENNICHITE` などを送る。
ブリッジの盤面はサーバーの裁定の裏書きを受けていないので、規則 A1 の意味で立脚点を持たない。

### D: オペレーターが命じたとき

stdin の `resign` / `stop` / `quit`。検証しない。そのまま実行する。

オペレーターはブリッジにもエンジンにも見えない情報を持っている。
大会本部の指示、機材の異常、次の対局に間に合わせる判断。
根拠を要求できる立場ではないので、規則 A1 / A2 は適用しない。

これが唯一「盤面上の根拠なしに投了を送る」経路である。

### 参照実装との関係

この分割は参照実装から導いたものではない。
今日この境界を 3 回引き直した結果として残ったものである。
突き合わせると次のようになる。

- `usiToCsa.rb` は A で一切介入しない。非合法手も根拠の無い投了も誤宣言もそのまま送る。
  B も持たない（`stop` 後の `bestmove` を期限なく待つ）
- `ShogiHome` は A の非合法手で投了する（`createMoveByUSI` 失敗 → `onResign`）。
  これは A2 を欠いた介入である
- 本実装は A で非合法手にだけ介入し、その代替を投了ではなく直前の読み筋にした

## Disconnection Is a Loss (0007)

`shogi-server` は対局中の切断を `GameResultAbnormalWin` として扱い、切断側に `%TORYO / #RESIGN / #LOSE` を送る。
再接続による継続は存在しない。

したがって「再接続とバックオフ」ではなく「ソケットを絶対に落とさない」設計に予算を振る。

- socket task が TCP stream を排他所有し、エンジン I/O とログでブロックしない
- session core は `unwrap` / `expect` を持たず panic-free に保つ
- 周辺 task の panic は捕捉して警報に落とす

なお `BEGIN Position` に指し手が入るケースの処理は必要である。
buoy 対局と、運営が指し手入りで対局を立て直す場合に届く。

## Viewer Is a Separate Process (0008)

観戦ビューアは JSONL イベントログを tail する独立バイナリにする。
対局プロセスに HTTP サーバーを同居させない。

理由は、port bind 失敗、panic、依存クレートのアドレス空間共有が、
いずれも対局を落とす経路になることである。
broadcast channel の drop-on-lag が守るのは遅い購読者だけで、これらは守れない。

当初はもう一つ理由を挙げていた。
CSA クライアント仕様が大会 LAN の通信を
「TCP の指し手、ICMP echo、ARP」に制限し HTTP を禁じている、という点である。
これは運用像の想定違いだった。
大会にはクラウドインスタンスを借りて参加し、そこから大会サーバーへ接続する。
観戦は同じインスタンス上の loopback を `ssh -L` で手元へ引くので、NIC には何も出ない。
会場 LAN の制約はビューアの形を決める要因ではない。

上の「別プロセス」は、この理由が消えても独立に有効である。

盤面描画については、当初「`Position::to_svg` をサーバー側で使い SSE で流す最小構成」
と書いていた。自前ビューアの実装時にこれを覆し、最終的にビューア自体を手放した（0011）。

## Ponder Is Driven by the Bridge, Switched by the Engine (0009)

相手の手番での探索は bridge が駆動する。
エンジンは単独では ponder できない。探索が始まるきっかけは `go` だけで、
`go ponder` と `ponderhit` と `stop` を送るのは bridge の仕事である。

一方で bridge にも独自のスイッチは置かない。
意思表示の置き場は `USI_Ponder` 一箇所であり、`--setoption` で渡す通常のエンジン設定として扱う。
指定がなければエンジンの既定に従う。

当初は `BridgeConfig::ponder` と `--ponder` を別に持っていたが、これは誤りだった。
同じ 1 つの事実を 2 箇所で言うことになり、片方だけ設定すると黙って何も起きない。

ただし判定は bridge 側で行う。エンジンに委ねられない。
YaneuraOu v9.40 は `setoption name USI_Ponder value false` を受けた後でも
`bestmove 2g2f ponder 8c8d` を返す（loopback 実測）。
このエンジンにとって `USI_Ponder` は時間配分の設定であって、
予測手を出すかどうかの設定ではない。

したがって bridge は「自分がエンジンに送った `USI_Ponder` の値」を読み返して守る。
スイッチは 1 つのまま、エンジンの実装に依存しない。

判断は 4 つある。

**開始はエコー後にする。**
盤面は `,T` エコーでしか進まず、ponder 局面は「自分の手 + 予測手」の後の盤面である。
floodgate 実測でエコーは数十 ms で返るので、存在しない局面を探索し始める危険を買う理由がない。

**予測手も合法性ゲートを通す。**
`csa_for_usi` は自分の手のために書いたものだが、
相手の手にもそのまま使える。通らない予測は捨てて ponder しない。

**予測の一致判定は CSA 表記で行う。**
サーバーから届くのは CSA なので、比較をそこに寄せれば USI 表記の揺れが判定に混ざらない。

**外した ponder は「解放待ち」にし、grace ではなく本来の着手期限で縛る。**
`bestmove` にはどの `go` への応答かを示す印がないため、
未応答の探索が 1 つでもある間は次の `go` を出せない。
ここで stop grace（1 秒）を使うと、解放が少し遅いだけのエンジンを投了させてしまう。
一方こちらの時計は満額残っているので、待てる限界は通常の着手期限そのものである。
外した瞬間に `stop` を送り、その doomed な探索に本来の期限を張る。
速やかに解放されれば期限ごと捨てて本探索に入り、
解放されなければ hang ladder が結局同じ時刻に走る。

構造上の保証として、`SearchKind::Ponder` のままの探索の `bestmove` は絶対に着手しない。
ponder を着手可能な答えに変えるのは `ponderhit` だけである。

## Conformance to the Published Spec (0010)

CSA 公式仕様 ver.1.2.1（server / client）を 1 項目ずつ実装と照合した。
結果は `agent-docs/tasks/0006-csa-spec-conformance/` にある。

このリポジトリの正本は `shogi-server` の実装であり、prose の仕様書ではない。
両者が食い違う場合は実装に従う。

具体例として、仕様はログイン名とパスワードを 32 バイト以内としているが、
floodgate で現に通っているパスワードは 42 バイトある。
prose に従って検査を足すと、動いている設定を自分で弾くことになる。

一方、仕様にしか書かれていない要求で、実装が満たしていなかったものが 2 つあった。
`To_Move` の検証と、明示的な `LOGOUT` である。どちらも対応した。

## The Viewer Lives Outside This Repository (0011)

観戦・事後検証・棋譜変換はこのリポジトリの責務ではない。
JSONL イベントログを書くところまでが bridge の仕事で、読む側は別リポジトリに置く。

一度は自前で実装した。`rsshogi-csa-watch` という 1 crate・3 サブコマンド
（`serve` / `export` / `status`）で、floodgate の実ログで監査も通した。
それを退役させた理由と、そのとき手放さなかったものを記録する。

**退役させた理由は、同じ利用者が既に観戦 UI を持っていることである。**
ShogiArena は盤面・持駒・棋譜・評価値グラフ・ライブカードを持つ。
寄せる先があるなら 2 つ持つ理由が無い。
「動くかもしれない古い実装」を残すと、直す動機が生じた瞬間に 2 つ直すことになる。
observability の二重化は observability の劣化である。

依存の向きも正しい。ShogiArena がこちらの JSONL を読む。
JSONL は追加専用で公開された契約であり、まさにこのために設計されている。
こちらは何も引き受けない。0012 が「筋が良い」とした方の案である。

**イベントログの契約は退役で変えない。**
0010 の時点では、workspace 内の 2 つ目の consumer が
「追加専用」を機械的に強制する最も安い手段だった。
その consumer は消えたが、契約は消えていない。強制する主体が
別リポジトリ・別言語の consumer に移り、機械的な強制力が弱くなっただけである。

したがって `record.rs` の `wire_lines_round_trip_byte_for_byte` を残す。
これが唯一の機械的な守り手になる。`Deserialize` の derive も残す。
テストが要求するというだけでなく、「この形は読み戻せる」という宣言そのものが契約の一部である。
0010 で `&'static str` の 4 フィールドを wire 表現不変の enum に置き換えた判断も、
`entering_king_rule` だけ `String` に残した判断も、そのまま生きている。

**手放さなかった設計は、後継が引き継ぐべきものとして残す。**

- 畳み込みは 1 本にする。live 観戦と事後検証は、同じ計算をカーソル位置違いで止めたものである。
  `.csa` 変換（0007 の D9 がここへ割り当てた）も、同じ畳み込みを描画せず直列化するだけである
- 未知の record type は reader 側で保持する。
  新しい bridge が古い reader を止められる状態は、追加専用スキーマの意味を失わせる
- `.csa` は文字列組み立てではなく局面再生で作る。価値は棋譜そのものではない。
  ログの指し手列を再生し直すことが bridge と reader の相互監査になる。
  再生に失敗した対局は黙って書かない
- 時計は 2 種類ある。台帳値は `,T` エコーから再構成した確定値、
  秒を刻む表示は client 側の推定である。両者を視覚的に区別し、
  推定は台帳値を超えられないよう上限を張る

**失うと分かって手放したものが 2 つある。**
ひとつは実ログに対する oracle で、後継の畳み込みが正しいかを確かめる相手が消える。
削除前に基準値を採取し、`agent-docs/tasks/0011-watch-retirement/decisions.md` の D3 に置いた。
記録したのは対局ログではなく、数十個の数値と checksum である。

もうひとつは zero-install の退路で、バイナリ 1 個を scp すれば観戦できる経路が無くなる。
観戦 UI を対局マシンで走らせる前提では実害ゼロだが、
それが無いマシンでシーズンを回すことになったら退路はもう無い。承知のうえで消した。

**0008 は変わらない。** 観戦を対局プロセスに同居させない、という境界は今も有効である。
むしろ読む側がリポジトリごと分離されたことで、より強く守られている。

## ShogiArena に読ませる案を採らない (0012)

以下は自前ビューアを持っていた時点の調査である。
「こちらのログを向こうの store へ流し込む」案を却下した記録であり、その結論は今も有効である。
末尾で「筋が良い」とした逆向きの案を最終的に採ったのが 0011 で、
`csawatch` への言及はその時点の実装を指す。

観戦 UI を自前で持たず、ShogiArena のダッシュボードに
イベントログを読ませればよいのではないか、という案を検討して却下した。
見た目は ShogiArena の方が良く、実際 0011 で見た目だけは寄せている。

**ShogiArena には外部からの取り込み口が無い。**
Python ツリー全体に CSA / KIF / レコードの ingestion は存在しない。
読むのは自分の store だけである。
`shogiarena dashboard serve` が要求するのは run ディレクトリで、
中身は 7 テーブルの SQLite（`game_move.next_move` は整数の指し手表現、
終局は sentinel 行）、worker の hydration 成果物、profile 推定用のメタデータである。
ここへ流し込むということは、別リポジトリの内部形式を我々が byte 互換で再現し、
向こうのリリースごとの変更をこちらが吸収し続けることを意味する。
D2 が避けた「2 つ目のスキーマ」を、リポジトリ境界を越えて、
JSONL より一桁広い相手に対してやることになる。

**ライブ観戦はそもそもできない。**
`resolve_archive_databases` は writer が DB を掴んでいると
`ArchiveDatabaseLivenessError` で拒否する。設計上、事後専用である。
ライブ配信の側は in-process の `EventBus` から来ており、
メッセージは `worker_idx` で識別される。
つまり「自分が回している対局の N 番目の worker」という形しか無い。
アーカイブ配信モードでは publisher が存在しない。

**仮に繋いでも、要るものが表示されない。**
phase、alert、`MoveOrigin` の fallback、着手期限、サーバー由来の時計、
ponder の的中率。いずれも向こうのスキーマにも UI にも置き場が無い。
異常検知のためのパネルを、見た目と引き換えに失うことになる。

**事後検証は既に解決している。**
`csawatch export` が出す `.csa` は ShogiHome でも floodgate の棋譜ページでも開く。
重い UI で並べたいときの経路は最初からある。

依存の向きを逆にした案（ShogiArena 側が我々の JSONL を読む importer を持つ）は筋が良い。
JSONL は追加専用で公開された契約であり、まさにこのために設計されている。
ただしそれは向こうのリポジトリの仕事であり、こちらは何もしない。

## Death Must Be Observable (0013)

外部から kill された bridge は、死んだ痕跡を何も残さない。
`game_end` も alert も書かれず、ログは `phase: playing` のまま途切れる。
読み手からは「長考中の対局」と区別できない。

2026-08-05 の floodgate 運用で実際に踏んだ。
落とされた対局が観戦側に「進行中」として何時間も残り続けた。

**推測で隠すのは誤りである。**
沈黙をもって死と判定して非表示にすると、動いている対局を隠す危険がある。
観戦ツールにとっては、止まった対局を見せる誤りより、
**動いている対局を隠す誤りの方が重い**。
だから隠すのではなく、観測可能にする。

`heartbeat` と `bridge_stop` を追加専用で足した（0011 D4 の行使）。

**heartbeat は沈黙を埋める。** 固定パルスではない。
直近 60 秒間に何のレコードも書いていなければ書く。
対局中は move / go / ponder が流れるので自然に抑制され、
長考とペアリング待ちの無音だけが埋まる。
保証されるのは 1 行の不変条件である
——**生きている bridge のログは、レコード間隔が 60 秒を超えない**。

**`bridge_stop` は完結の宣言である。**
`state { phase: closing }` は shutdown の開始であって完了ではない。
closing 中に kill されれば closing が最終レコードのまま途切れる。
「このログは完結している」と言えるのは `bridge_stop` だけである。

どちらもフィールドを持たない。envelope の時刻がメッセージの全内容であり、
phase は `state` が既に答えている。二重の真実を作らない。

**間隔は設定にしない。** 読み手は書き手と間隔を交渉できない。
設定可能にすると、片方が黙ってもう片方の判定閾値を無効化できてしまう。

**検出限界は主張しない。** SIGKILL では何も書けないので、
`bridge_stop` は正常終了の証明にしかならず、異常終了は heartbeat の途絶でしか分からない。
書き込みは OS バッファを経るので電源断では heartbeat 自体が失われうる。
保証できるのは「kill から 60 秒 + flush 遅延 + 読み手の poll 間隔以内」である。

**読み手を先に出す。** 書き手が先だと、読み手にとっては未知 record type なので、
健全な全 run のログ健全性欄が「未知 type」で埋まり、鳴りっぱなしの警報になる。

なお heartbeat は `next_deadline` に混ぜない。
あれはプロトコルが課す期限を報告するもので、heartbeat はログの刻みである。
混ぜた実装を試して seam テストが 5 本落ちたが、
**落ちたこと自体が設計の取り違えの指摘だった**ので、期待値ではなく設計を直した。
